# M8: the maintained release and user update workflow

**Completed locally, 2026-11-02.** All three candidates carried one Ruff owner
change through generated metadata, two ordinary wheel releases, an update in
the same uv project, ordinary uvx, the same native prefix/profile, and the
actual public Bazel Ruff target. Worktree owner pins remain unchanged: release
A 0.8.0 uses current owners, while isolated maintained-source copies produce
B 0.8.1 with Ruff 0.14.6. Package names are local fixtures; no public identity,
hosting choice, publication or adoption is decided.

The maintenance distinction is in the producer. Mise and Aqua accept an exact
Ruff release in their native owner configuration. Nix selects the Ruff package
from a separately locked package input, retaining the other package versions.
All three still own SCORE's ordinary dependency-package export and the portable
Bazel compatibility adapter. Their Python users make the same kind of update:
change the facade release requirement, then let uv resolve the generated Ruff
pin. Prepared native commands also run directly after provisioning.

## What M8 adds

[Round three](tooling-version-workflow-comparison.md) already demonstrated
owner-derived metadata and real uv/uvx use in bounded experiments.
[M6](tooling-integration-milestone.md) moved packaging to maintained paths, and
[M7](tooling-platform-milestone.md) exercised prepared ARM64 output. M8 adds a
complete sequence through those maintained APIs: stale owner/export rejection,
owner-bound A/B artifacts handed outside the source tree, rejection of A against
B owners, the same consumer and native installation updated in place, and an
actual updated `//tools:ruff` execution preserving cwd, argv and nonzero status.
The [shared contract](../experiments/tool-manager-comparison/release-workflow-milestone.md)
and [compact evidence archive](../experiments/tool-manager-comparison/release-evidence/README.md)
define the tested boundary.

The target 0.14.6 and its historical Nixpkgs snapshot were supplied from prior
knowledge. Nix did not discover an arbitrary requested version automatically.
Mise/Aqua also depended on the requested upstream release and supported assets
existing; their backends resolved this known target without a new Ruff recipe.

Exact commands, both wheel `Requires-Dist` snapshots, consumer TOMLs and uv.lock
states, native records and Bazel command results are archived per candidate.
The tested Nix full-prepare path emits a native closure alongside facade source.
That work serves native delivery; it is not required of the ordinary Python
consumer or a property of building an ordinary wheel. Package-only generation
from a validated release remains available.

Mise's tested uvx form uses `--from` the facade; Aqua uses `--with` the facade;
Nix uses `--with` the facade plus `--from ruff`. These are ordinary resolver
forms, without a consumer-authored Ruff pin or SCORE launcher. The wheel
handoff contains dependency metadata; native prefix/profile delivery is a
separate output from the same authority, not installation of that wheel as a
native manager profile.

## Shared policy and continuing manager duties

SCORE owns the public command/extra identities, selection maps, artifact-release
binding and portable Bazel URL/hash/archive-layout adapter in every candidate.
Mise/Aqua also retain SCORE's owned-prefix reconciliation and selected-output
allowlist. Nix supplies native profile replacement/removal; SCORE chooses the
profile map and compatibility exports. These mechanisms are not interchangeable
implementations of one fixed-prefix reconciler.

The normal Python consumer needs compatible Python/uv, the selected wheel,
and dependency-index access or populated metadata/wheel caches. It needs no
producer manager, source checkout or Bazel. A native user needs the candidate's
manager during reprovisioning; prepared tool calls use the resulting executable
directly. Optional strict `tools/run-tool` verification exercised that direct
path under poisoned manager/Bazel PATH. The separate Bazel test explicitly
invokes Bazel as an existing compatibility consumer.

For another supported platform, check existing backend/registry/package support
and provide only missing bootstrap, asset/checksum, recipe or runtime data.
Mise and Aqua retain portable-layout mappings; Aqua retains APM's adjacent
runtime tree. Nix retains target package availability, custom assets such as
OpenCode, closure production/transfer and activation. Existing data may already
cover a platform. No platform recipe was added for this Ruff update, and no
harness repair demonstrates that new repair work must recur on every platform.
Consumer transitive Python resolution belongs to its uv.lock; wheel hashes bind
these built artifacts, without establishing a fully locked build toolchain.

## Actual repairs and justified cleanup

- **Mise:** replaced assertion-only owner/lock equality with an explicit stale
  error that remains active under optimized Python. The affected four-test
  module and its Bazel test passed. The maintained release guide replaces
  superseded Git-selected `score-tool` examples and duplicate fixed-version
  wheel snippets. Bootstrap, refresh, package, provision and public compatibility
  entrypoints remain because they still serve distinct exercised boundaries.
- **Aqua:** needed no implementation repair. A maintained guide consolidates
  the older release snippet. No helper was demonstrated redundant: owner
  refresh, export/check, package preparation/check and provisioning remain
  distinct operations. Initial missing small catalog configuration was a staging
  harness problem. Current limits include traceback-style stale reporting,
  a fresh-directory smoke checker and cache-backed native recopy/reinstall.
- **Nix:** added optional `--reuse-native-from`, with two new inode/symlink and
  missing-object tests (nine focused tests passed). It reuses trusted immutable
  store files on the same filesystem while keeping directories and release
  metadata independent. This is a local storage/release-efficiency option,
  not an inherent migration prerequisite. Removed the obsolete standalone
  Dockerfile and its export: it referenced the old comparison image and a
  missing installer. Fresh preparation without it preserved the required
  release/package/activation output. Package-only generation, smoke helpers,
  membership regression and historical reports were retained with reasons.

These source changes are separate from per-version owner edits in the isolated
copies. Supported final sequences now live in each candidate's maintained
`tools/internal/{mise,aqua,nix}/README.md`; the archived M8 reports reproduce the
commands and prerequisites. Recorded transcripts need fresh destinations and
correct A/B state; they are not blindly repeatable orchestration scripts.

## Evidence and limits

The [archive index](../experiments/tool-manager-comparison/release-evidence/README.md)
links compact handoffs, structured command results, authored and generated
diffs, metadata/locks, source-change and owner-continuity records, and
[provenance](../experiments/tool-manager-comparison/release-evidence/provenance.json).
It contains no runtime trees, full logs or maintained-source copies. Root's
[independent review](../experiments/tool-manager-comparison/release-evidence/root-review.json)
confirms source deltas, affected unit checks and actual wheel/consumer-lock
bindings. The writer also checks original/archive hashes, final owner/source
claims, licenses, links and sizes. Runtime execution remains the source workers'
recorded execution; the review does not imply an independent runtime rerun.

M8 ran on Linux amd64 with existing caches and online acquisition. Explicit
offline uv flags and poisoned PATH checks do not establish OS network isolation.
Native updates ran under the same unprivileged owner per candidate; Nix used a
UID65534 profile and daemon, while Python/Bazel consumers used host uid 1000.
No new full image, native ARM/macOS execution or hosted release was tested.
M6/M7 results remain tied to their recorded source hashes; M8 reran the affected
checks described above, not the six full M6 integration gates. No lifetime
maintenance estimate, equivalent managerless M8 evaluation, winner or completed
whole migration follows from this bounded release workflow.
